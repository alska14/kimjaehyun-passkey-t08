# 인증 구현 설명서 (T08 · 소개 페이지에 패스키 달기)

[본인 확인 필요] 표시가 있는 문장은 제출 전에 직접 읽고, 사실과 다르면 고쳐 쓰세요.

## ① 무엇으로 붙였나

- 브라우저: 기본 WebAuthn API(`navigator.credentials.create / get`)를 `public/passkey.js`에서 직접 호출합니다.
- 서버: Vercel 서버 함수(`api/auth/[action].js`, `api/private/[action].js`)에서 `@simplewebauthn/server` 14.x 라이브러리로 등록·서명 검증을 합니다.
- 저장소: Supabase(Postgres). 공개키, 일회용 질문(challenge), 세션 해시, 비공개 메모를 서버 전용 키로만 읽고 씁니다.
- 쓰지 않은 것: 비밀번호, OAuth·소셜 로그인, 외부 인증 서비스(Auth0 등), CAPTCHA.

## ② 왜 그걸 골랐나

- 서명 검증은 암호 코드라 직접 짜면 틀리기 쉽습니다. 그래서 검증 부분만 널리 쓰는 라이브러리에 맡겼습니다.
- 질문 발급·1회 사용 처리, 세션, 소유자 검사는 직접 짰습니다. 어디서 막히는지 설명할 수 있어야 하는 과제이기 때문입니다.
- Supabase는 7번 과제에서 이미 써 본 도구라 새로 배울 것이 적었습니다. [본인 확인 필요: 실제로 이 이유로 골랐는지]
- 휴대폰과 PC 모두에서 되게 하려고 등록할 때 저장 위치를 고르게 했습니다: 이 기기(Windows Hello·지문·PIN), 휴대폰(QR로 연결), USB 보안 키, 브라우저가 고르게 하기. 서버는 선택에 따라 WebAuthn의 `hints`와 `authenticatorAttachment`만 바꾸고, 로그인은 어떤 저장 위치의 패스키든 같은 방식으로 검증합니다. 처음에는 선택 없이 브라우저에 맡겼는데, PC에서 Windows가 USB 보안 키부터 요구하는 문제가 있어 고쳤습니다.

## ③ 어디를 어떻게 고쳤나

1번 소개 페이지(`ai-pair-log/index.html`, 1번 결과물 https://alska14.github.io/kimjaehyun-portfolio/)를 그대로 `public/index.html`로 가져와 메뉴 링크 하나, 스타일 블록 하나, 비공개 섹션 하나, 스크립트 한 줄만 더했습니다. 원본과 비교해 추가한 부분만 빼면 글자 하나까지 같습니다. 공개 내용은 지우거나 바꾸지 않았습니다.

| 위치 | 한 일 |
|---|---|
| `public/index.html` | 메뉴에 "🔒 비공개", 페이지 아래쪽에 점선 상자로 공개·비공개 경계가 보이는 `#vault` 섹션. 비공개 내용은 HTML에 없음 |
| `public/passkey.js` | 등록, 로그인, 로그아웃, 패스키 목록·추가·삭제, 메모 추가 화면 |
| `api/auth/[action].js` | 등록 질문 발급·검증, 로그인 질문 발급·검증, 로그아웃, 세션 확인 |
| `api/private/[action].js` | 메모와 패스키 목록·삭제. 쿠키 세션이 없으면 401 |
| `lib/` | 저장소, 쿠키·세션·출처 검사 |
| `db/schema.sql` | 테이블 5개와 권한 회수(RLS) |

흐름은 이렇습니다.

1. 등록: 서버가 일회용 질문을 만들어 DB에 저장하고 브라우저에 보냅니다. 기기가 공개키·개인키 한 쌍을 만들어 공개키와 서명만 돌려줍니다. 서버는 질문을 "사용됨"으로 바꾼 뒤 검증하고, 통과하면 공개키를 저장합니다. 개인키는 서버로 오지 않습니다. 계정과 패스키는 이 검증이 끝난 뒤에야 만들어지므로, 중간에 취소하면 아무것도 남지 않습니다.
2. 로그인: 매번 새 질문을 보내고 기기가 개인키로 서명합니다. 서버가 저장해 둔 공개키로 서명을 확인한 뒤에만 세션을 줍니다. 세션 토큰은 무작위 32바이트이고, DB에는 해시만 저장합니다. 쿠키는 `HttpOnly; SameSite=Strict; Secure`이며 1시간 뒤 만료됩니다.
3. 비공개 요청: 쿠키의 세션으로만 사용자를 정합니다. 주소나 본문에 적힌 사용자 ID는 읽지 않습니다.
4. 로그아웃: DB의 세션 행을 지웁니다. 같은 쿠키 값으로 다시 요청해도 401입니다.

패스키는 계정당 여러 개 등록할 수 있습니다. 마지막 하나는 지울 수 없습니다(409). 지우면 그 계정으로 다시 들어올 방법이 없기 때문입니다. 패스키 목록에는 이름, 등록·마지막 사용 시각, 저장 위치(기기 전용인지, 구글 비밀번호 관리자·iCloud로 동기화되는지)가 보입니다. 저장 위치는 등록 때 인증기가 알려 준 값(`credentialDeviceType`, `credentialBackedUp`)입니다.

## ④ 안 열리는 것을 확인한 기록

`scripts/e2e.mjs`가 크롬 가상 인증기로 실제 서버에 요청을 보내 확인합니다. 결과는 `evidence/e2e-result.json`, 화면은 `evidence/*.png`입니다.

로컬 서버를 실제 Supabase에 붙여 33개 확인이 모두 통과했습니다(메모리 저장소로도 같은 결과). 이 중 핵심 네 가지입니다.

| 확인 | 결과 |
|---|---|
| 패스키 없이 비공개 API 요청 | 401 (`/api/private/items`, `/api/private/passkeys`) |
| 이미 쓴 질문으로 로그인 재시도 | 400 `CHALLENGE_INVALID` |
| 서명이 틀린 로그인 요청 | 401, 세션 쿠키 없음 |
| 로그아웃 뒤 같은 세션 값으로 요청 | 401 |

그 밖에 남의 계정으로 가는 요청도 확인했습니다. 계정 B가 A의 패스키 삭제를 요청하면 404이고, 주소나 본문에 A를 적어도 B의 자료만 돌아옵니다. 로그인 질문과 등록 질문은 요청마다 값이 달랐습니다. 지운 패스키를 가진 기기로 로그인하면 거절됩니다.

주의: 이 기록은 가상 인증기와 로컬 서버에서 얻은 것입니다. 배포한 주소와 실제 기기(노트북, 휴대폰)에서 같은 확인을 한 기록은 제출 전에 본인이 남겨야 합니다. 방법은 `docs/제출-체크.md`에 있습니다.

## ⑥ 아직 못 막은 것

- 시도 횟수 제한이 없습니다. 서명이 필요해서 대입이 어렵지만, 질문 발급 요청을 계속 보내는 것은 막지 못합니다.
- 만료된 질문과 세션 행을 지우는 정리 작업이 없습니다. 쌓이기만 합니다.
- 계정 복구는 두 번째 패스키뿐입니다. 패스키가 하나뿐인 기기를 잃어버리면 이 계정에는 들어올 수 없습니다.
- 세션은 1시간 고정이고 연장·기기별 목록·강제 로그아웃 기능이 없습니다.
- 서버가 요청 헤더의 호스트로 RP ID를 정합니다. 배포에서는 `RP_ID`, `ORIGIN` 환경변수로 고정하는 편이 더 안전합니다.
- 비공개 메모 기본 3건은 서버가 만든 예시 문구입니다. 실제 개인정보는 넣지 않았습니다.
- 실제 Supabase 연결 시험은 로컬 서버에서 했습니다. Vercel에 배포한 주소에서의 시험은 배포 후 `scripts/e2e.mjs`를 한 번 더 돌려야 합니다.
