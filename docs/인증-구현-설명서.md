# 인증 구현 설명서 (T08 · 소개 페이지에 패스키 달기)

이 문서의 ⑤번은 작업 중 실제로 오간 대화와 시험 결과를 바탕으로 썼습니다.

## ① 무엇으로 붙였나

- 브라우저: 기본 WebAuthn API(`navigator.credentials.create / get`)를 `public/passkey.js`에서 직접 호출합니다.
- 서버: Vercel 서버 함수(`api/auth/[action].js`, `api/private/[action].js`)에서 `@simplewebauthn/server` 14.x 라이브러리로 등록·서명 검증을 합니다.
- 저장소: Supabase(Postgres). 공개키, 일회용 질문(challenge), 세션 해시, 비공개 메모를 서버 전용 키로만 읽고 씁니다.
- 쓰지 않은 것: 비밀번호, OAuth·소셜 로그인, 외부 인증 서비스(Auth0 등), CAPTCHA.

## ② 왜 그걸 골랐나

- 서명 검증은 암호 코드라 직접 짜면 틀리기 쉽습니다. 그래서 검증 부분만 널리 쓰는 라이브러리에 맡겼습니다.
- 질문 발급·1회 사용 처리, 세션, 소유자 검사는 직접 짰습니다. 어디서 막히는지 설명할 수 있어야 하는 과제이기 때문입니다.
- 저장소는 Supabase와 Vercel KV 중에서 정했습니다. 차이를 AI에게 물었고, 이미 7번 과제에서 써 본 Supabase가 새로 연결할 서비스가 없어 덜 번거롭다는 설명을 듣고 Supabase로 진행했습니다.
- 구글 인증기·카카오 인증기 같은 앱 방식을 쓰면 더 낫지 않느냐고 물었습니다. 그 방식은 6자리 숫자를 서버와 나눠 갖는 다른 방식이고, 과제가 요구하는 "공개키를 저장하고 서명을 확인하는" 방식이 아니라는 설명을 듣고 패스키로 진행했습니다.
- 휴대폰과 PC 모두에서 되어야 한다는 요구는 내가 했습니다. 그래서 특정 기기 전용으로 제한하지 않고, 처음에는 등록할 때 저장 위치(이 기기 / 휴대폰 QR / USB 보안 키 / 브라우저가 고르게 하기)를 고르게 했습니다. 이 방식이 실제 기기에서 헷갈린다는 것을 시험으로 알게 되어 나중에 단순하게 바꿨습니다(⑤번 참고).

## ③ 어디를 어떻게 고쳤나

1번 소개 페이지(`ai-pair-log/index.html`, 1번 결과물 https://alska14.github.io/kimjaehyun-portfolio/)를 그대로 `public/index.html`로 가져와 메뉴 링크 하나, 스타일 블록 하나, 비공개 섹션 하나, 스크립트 한 줄만 더했습니다. 원본과 비교해 추가한 부분만 빼면 글자 하나까지 같습니다. 공개 내용은 지우거나 바꾸지 않았습니다.

| 위치 | 한 일 |
|---|---|
| `public/index.html` | 메뉴에 "비공개 자리", 페이지 아래쪽에 점선 상자로 공개·비공개 경계가 보이는 `#vault` 섹션. 비공개 내용은 HTML에 없음 |
| `public/passkey.js` | 등록, 로그인, 로그아웃, 패스키 목록·삭제, 다른 기기 연결(링크·코드), 메모 추가 화면. 기기 이름은 자동으로 붙임 |
| `api/auth/[action].js` | 등록 질문 발급·검증, 로그인 질문 발급·검증, 로그아웃, 세션 확인 |
| `api/private/[action].js` | 메모와 패스키 목록·삭제, 연결 코드 발급. 쿠키 세션이 없으면 401 |
| `lib/` | 저장소, 쿠키·세션·출처 검사 |
| `db/schema.sql` | 테이블 5개와 권한 회수(RLS) |

흐름은 이렇습니다.

1. 등록: 서버가 일회용 질문을 만들어 DB에 저장하고 브라우저에 보냅니다. 기기가 공개키·개인키 한 쌍을 만들어 공개키와 서명만 돌려줍니다. 서버는 질문을 "사용됨"으로 바꾼 뒤 검증하고, 통과하면 공개키를 저장합니다. 개인키는 서버로 오지 않습니다. 계정과 패스키는 이 검증이 끝난 뒤에야 만들어지므로, 중간에 취소하면 아무것도 남지 않습니다.
2. 로그인: 매번 새 질문을 보내고 기기가 개인키로 서명합니다. 서버가 저장해 둔 공개키로 서명을 확인한 뒤에만 세션을 줍니다. 세션 토큰은 무작위 32바이트이고, DB에는 해시만 저장합니다. 쿠키는 `HttpOnly; SameSite=Strict; Secure`이며 1시간 뒤 만료됩니다.
3. 비공개 요청: 쿠키의 세션으로만 사용자를 정합니다. 주소나 본문에 적힌 사용자 ID는 읽지 않습니다.
4. 로그아웃: DB의 세션 행을 지웁니다. 같은 쿠키 값으로 다시 요청해도 401입니다.

다른 기기(휴대폰 등)를 같은 계정에 연결하는 방법은 연결 코드입니다. 로그인한 기기에서 "다른 기기 연결"을 누르면 서버가 10분짜리 일회용 연결 코드(XXXX-XXXX-XXXX, 12자, 헷갈리는 글자 제외)를 만들고(DB에는 해시만 저장), 코드와 링크 `https://…/?link=코드`를 보여 줍니다. 새 기기가 이 링크를 열거나 사이트 첫 화면에서 코드를 직접 입력하고 지문·얼굴·PIN으로 확인하면 그 기기의 패스키가 같은 계정에 추가됩니다. 코드는 등록 검증이 끝날 때 한 번만 소모되며, 중간에 취소하면 다시 시도할 수 있습니다.

패스키는 계정당 여러 개 등록할 수 있습니다. 마지막 하나는 지울 수 없습니다(409). 지우면 그 계정으로 다시 들어올 방법이 없기 때문입니다. 패스키 목록에는 이름, 등록·마지막 사용 시각, 저장 위치(기기 전용인지, 구글·iCloud로 동기화되는지)가 보입니다. 저장 위치는 등록 때 인증기가 알려 준 값(`credentialDeviceType`, `credentialBackedUp`)입니다.

### 소스 위치: 네 가지 흐름이 지나가는 곳

| 흐름 | 지나가는 소스 |
|---|---|
| 등록 | `public/passkey.js`의 `register` → `api/auth/[action].js`의 `registerOptions`(25행, 질문 발급·저장) → 기기가 패스키 생성 → `registerVerify`(79행, 질문 소모 87행, 서명·공개키 검증 95행) → `lib/db.mjs`의 `createUserWithPasskey` |
| 로그인 | `passkey.js`의 `login` → `loginOptions`(147행, 새 질문) → 기기가 서명 → `loginVerify`(156행, 질문 소모 162행, 패스키 조회 168행, 서명 검증 175행) → `lib/http.mjs`의 `startSession`(65행) |
| 로그아웃 | `logout`(`api/auth/[action].js` 198행) → 서버의 세션 행 삭제, 쿠키 만료 |
| 비공개 자료 조회 | `api/private/[action].js` 17~21행: `currentUser`(`lib/http.mjs` 79행)로 쿠키의 세션을 확인하고 없으면 401 → 25행: 세션 주인의 메모만 `listItems(user.id)`로 조회 |

거절을 만들어 내는 소스의 위치는 이렇습니다.

| 거절 | 소스 위치 |
|---|---|
| 로그인 없이 비공개 요청 → 401 | `api/private/[action].js` 17~21행 |
| 이미 쓴 질문 → 400 `CHALLENGE_INVALID` | `api/auth/[action].js` 162~165행. 질문 소모는 `lib/db.mjs` 23행에서 `used_at`이 비어 있는 행만 한 번에 갱신 |
| 틀린 서명, 삭제된 패스키 → 401 `LOGIN_FAILED` | `api/auth/[action].js` 168~172행(DB에 없는 패스키), 175~190행(서명 검증 실패) |
| 남의 패스키 삭제 → 404 | `api/private/[action].js` 57행(내 패스키 목록에 없으면 404). 삭제 쿼리도 `lib/db.mjs` 67행에서 `user_id` 조건을 함께 씀 |
| 마지막 패스키 삭제 → 409 | `api/private/[action].js` 59행 |

### 세션 방식

로그인한 사람을 알아보는 값은 **세션**입니다. 서버가 무작위 32바이트 값을 만들어 쿠키(`sid`, HttpOnly)로 주고, DB에는 그 값의 해시와 만료 시각만 저장합니다. JWT 같은 서명된 토큰은 쓰지 않았습니다. 로그아웃하면 DB의 세션 행이 지워져서 같은 쿠키 값이 바로 무효가 됩니다.

### 패스키가 저장된 곳

내가 실제로 등록한 패스키 두 개입니다.

- PC: Chrome에서 **구글 비밀번호 관리자**에 저장 (이름 `pc`).
- iPhone: Safari에서 **iCloud 키체인**에 저장 (이름 `iPhone · Safari`).

이 사이트는 어디에 저장됐는지를 직접 알지 못하고, 등록 때 기기가 알려 주는 `credentialDeviceType`(`multiDevice` = 동기화되는 패스키)과 `credentialBackedUp`(`true` = 클라우드에 백업됨) 값을 보여 줍니다. 두 패스키 모두 `multiDevice`, `backedUp=true`로 기록되어 있습니다.

### 넣은 내용에 대해

비공개 자리의 메모 3건은 서버가 만들어 넣은 **예시 문구**이고, 계정의 표시 이름도 별명입니다. 실제 연락처, 신분증 번호, 비밀값은 어디에도 넣지 않았습니다. 시험용 계정과 메모도 모두 만들어 넣은 값입니다.

가상 인증기는 실제 기기가 아닙니다. 실제 기기에서는 내가 직접 확인했습니다.
- PC Chrome(구글 비밀번호 관리자)으로 패스키 `pc`를 등록하고 로그인했습니다.

- 시험을 반복하려고 휴대폰 패스키를 서버에서 지운 뒤 다시 연결했고, 화면에 패스키 두 개가 보였습니다.
- 화면 증거: 첨부한 `과제 8 스크린샷.png`에 패스키 두 개(`pc`, `iPhone · Safari`)가 이름·등록 시각·저장 위치와 함께 보입니다.

## ⑤ AI와 나

### AI가 한 일
- 설계: 질문 1회 사용, 세션 해시 저장, 소유자 검사, 마지막 패스키 삭제 금지, 연결 코드 방식.
- 구현: 서버 함수, 화면, DB 스키마, 시험 스크립트(48개 확인). 가상 인증기로 시험하고 배포 주소에서도 같은 시험을 돌렸습니다.
- 내 요청으로 한 운영 작업: GitHub 공개 저장소 생성과 푸시, 시험으로 생긴 테스트 계정 삭제, 중복 계정(`재현폰`) 삭제, 다시 시험하려고 휴대폰 패스키 삭제. 이 작업에 `.env.local`의 서버 전용 키를 썼고 키 값은 화면이나 문서에 출력하지 않았습니다.
- 내 파일을 고친 일: 메모장이 `.env.local.txt`로 저장한 파일 이름을 바꾸고, 주소 끝에 붙은 `/rest/v1/`를 지웠습니다. 키 값은 건드리지 않았습니다.

### 내가 직접 하거나 판단한 일
- 1번 소개 페이지 선택: AI는 처음에 `fortpolio/index.html`을 1번 페이지로 가정했습니다. 내가 바탕화면 `ai-pair-log`의 `index.html`이 내 포트폴리오라고 바로잡았고, 그 파일로 교체했습니다.
- 인증 방식과 저장소 선택: 위 ②번의 두 질문(인증기 앱 방식, Supabase vs Vercel KV)과 결정.
- 계정과 비밀값: Supabase 프로젝트 생성, 테이블 SQL 실행, Vercel 프로젝트 연결을 내가 했습니다. 서버 전용 키는 채팅에 붙이지 않고 `.env.local`과 Vercel 환경변수에 직접 넣었습니다.
- 실제 기기 시험과 그 결과로 방향을 바꾼 일(시간순):

| 내가 본 것 | 바뀐 결정 |
|---|---|
| 학원 PC 웨일에서 Windows가 USB 보안 키를 꽂으라고 함 | 등록할 때 저장 위치를 고르는 선택지를 넣음 |
| "이 기기" 선택 시 "기기를 사용할 수 없음". 이 PC에는 Windows Hello가 없음 | Chrome으로 열도록 안내받음 |
| Chrome에서 구글 비밀번호 관리자로 패스키 등록 성공 | PC 패스키는 Chrome + 구글 계정으로 확정 |
| "휴대폰(QR)" 선택 시 QR이 안 뜨고 USB 창이 뜸 | QR을 막던 설정을 고쳤지만 PC에 블루투스가 없을 가능성이 커 이 방법은 쓰지 않음 |
| 폰에서 "내 기기로" 등록하니 같은 이름의 별개 계정이 생김 | 로그인한 계정에 폰을 연결하는 방법이 필요하다고 판단 |
| 화면이 너무 복잡해서 헷갈림 | 내가 UI 단순화를 요청. 잠금 화면은 "패스키로 열기" 버튼 하나로 줄이고, 저장 위치 선택은 접어 두고, 패스키 이름은 자동으로 붙이게 바꿈 |
| 연결 링크를 폰 Safari에 직접 붙여 넣으면 성공, 카카오톡으로 보내 열면 연결이 안 됨 | 링크 형식을 `#` 뒤에서 `?link=` 쪽으로 옮김 |
| 카톡 카드에서 링크 뒤쪽이 잘려 보임 | 링크가 아니라 글자로 입력하는 연결 코드 방법을 추가 |

- 정리 요청: 중복 계정과 시험용 패스키를 지우라고 요청했습니다.

### AI 제안을 따르지 않았거나 하지 않은 일
- Windows Hello PIN 설정: AI가 제안했지만 하지 않았습니다. 대신 Chrome의 구글 비밀번호 관리자로 PC 패스키를 등록했습니다.
- 웨일용 Bitwarden·1Password 확장 설치: AI가 가능성으로 언급했지만 시도하지 않았습니다. 웨일에서는 패스키 등록을 지원하지 못한 채로 두었습니다.
- 휴대폰 QR 방식: 시도했지만 PC에서 QR이 뜨지 않아 쓰지 않았습니다.
- AI의 처음 판단이 틀렸던 것: 1번 페이지 위치, 처음의 복잡한 화면, `#` 뒤에 둔 연결 링크는 모두 내가 실제로 써 보고 문제를 알려서 고쳤습니다.

### AI가 하지 못했거나 확인하지 못한 일
- 실제 PC·휴대폰·카카오톡에서의 동작은 AI가 직접 볼 수 없었습니다. 내가 본 화면과 문구를 알려 주면 그에 맞춰 고쳤습니다.
- 카카오톡이 링크의 어느 부분을 어떻게 바꾸는지는 확인하지 못했습니다. `#` 뒤가 잘렸다는 설명은 내 관찰에서 나온 추정입니다.
- 제출 버튼은 AI가 누르지 않습니다.

### 제출 칸용 세 줄
- AI에게 맡긴 일: 설계(질문 1회 사용·세션 해시·소유자 검사), 서버·화면·DB 코드, 가상 인증기 시험 48개와 배포 주소 확인.
- 내가 판단한 일: 1번 페이지 위치 바로잡기, 패스키 방식과 Supabase 선택, 계정·키 직접 입력, 실제 PC·폰·카카오톡에서 써 보고 화면 단순화와 연결 코드·링크 방식으로 방향을 바꾼 것.
- 따르지 않거나 못 한 것: Windows Hello PIN 설정과 웨일 확장은 하지 않았고, 휴대폰 QR은 이 PC에서 안 돼 쓰지 않았으며, 카톡이 링크를 자르는 원인은 확인하지 못했습니다.

## ⑥ 아직 못 막은 것

- 시도 횟수 제한이 없습니다. 서명이 필요해서 대입이 어렵지만, 질문 발급 요청을 계속 보내는 것은 막지 못합니다.
- 만료된 질문과 세션 행을 지우는 정리 작업이 없습니다. 쌓이기만 합니다.
- 연결 코드는 가진 사람이 그 계정에 패스키를 추가할 수 있는 열쇠입니다. 10분 만료와 1회 사용으로 줄였지만, 메신저로 보내는 과정에서 새는 것은 막지 못합니다. 링크 형태일 때는 코드가 호스팅 서비스의 요청 로그에 남을 수 있습니다.
- 계정 복구는 두 번째 패스키뿐입니다. 패스키가 하나뿐인 기기를 잃어버리면 이 계정에는 들어올 수 없습니다.
- 세션은 1시간 고정이고 연장·기기별 목록·강제 로그아웃 기능이 없습니다.
- 서버가 요청 헤더의 호스트로 RP ID를 정합니다. 배포에서는 `RP_ID`, `ORIGIN` 환경변수로 고정하는 편이 더 안전합니다.
- 웨일처럼 패스키를 저장할 소프트웨어 저장소가 없는 브라우저와, 지문·PIN이 없는 PC에서는 등록이 되지 않습니다. 사이트 코드로는 고칠 수 없는 브라우저와 OS의 제한입니다. 휴대폰 QR 방식은 PC에 블루투스가 있어야 하는데 이 PC에서는 시험하지 못했습니다.
- 비공개 메모 기본 3건은 서버가 만든 예시 문구입니다. 실제 개인정보는 넣지 않았습니다.
